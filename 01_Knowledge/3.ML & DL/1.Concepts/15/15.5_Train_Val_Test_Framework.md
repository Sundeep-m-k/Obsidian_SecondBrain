# Train-Val-Test Framework

## What is it?

The **train-val-test split** is a three-way division of data, each with a specific purpose:

| Set | Size | Purpose | When Used |
|-----|------|---------|-----------|
| **Train** | 60-70% | Fit model parameters $\theta$ | Gradient descent, parameter learning |
| **Validation** | 10-15% | Tune hyperparameters $\lambda$ | Model selection, early stopping |
| **Test** | 10-15% | Final evaluation (look once) | Report performance to stakeholders |

**Golden rule:** Never train the model, and never tune hyperparameters, on the test set.

---

## Why Three Sets?

### With Only Train/Test

```
Train on 90%, test on 10%
If you tune hyperparameters by looking at test results:
  → Test set is no longer "held-out" — it's part of development
  → You optimize for test set properties, not generalization
  → Reported test accuracy is optimistic
```

Example: Try 100 hyperparameter settings, pick the one with best test accuracy. That setting is overfitted to test set. True generalization performance is lower.

### With Train/Val/Test

```
Train on 70%, val on 15%, test on 15%

1. Fit model on train
2. Tune hyperparams by trying many on val
3. Pick best based on val results
4. Train final model on train with best hyperparams
5. Report performance on test (look only once!)

Test set is truly unseen; not influenced by tuning.
```

---

## The Three Purposes: Never Mix

### Train Set: Learning

**Purpose:** Estimate model parameters $\theta$.

**What happens:**
- Gradient descent / EM / other optimization algorithm
- Model sees examples and adjusts $\theta$
- Training loss decreases (expected)

**Error:** Don't report training error as model performance — it's always lowest due to memorization.

### Validation Set: Hyperparameter Tuning

**Purpose:** Select hyperparameters $\lambda$ (learning rate, regularization strength, tree depth, etc.).

**What happens:**
- Train multiple models with different $\lambda$ values on **train set**
- Evaluate each on **val set**
- Pick the $\lambda$ with best val performance
- The val set is now part of the "development process" — don't report it as final performance

**Error:** If you use val set to make training decisions (e.g., early stopping) then report val error as test performance, you've leaked information.

### Test Set: Final Evaluation

**Purpose:** Report generalization performance.

**What happens:**
- Train final model (with best hyperparams) on **train set**
- Evaluate on **test set** once
- Report this number
- Never tune anything based on test results

**Error:** If you look at test results, get disappointed, try different hyperparams, train again, and report new test score, you've optimized for test set. The reported number is biased.

## Data Leakage: The Central Risk

**Data leakage** occurs when information from val or test sets influences training.

### Forms of Leakage

#### 1. Scaling / Normalization Leakage

```python
# ✗ WRONG: Fit scaler on all data
scaler = StandardScaler()
X_scaled = scaler.fit_transform(X)  # Fits on ALL examples
X_train = X_scaled[:70]
X_val = X_scaled[70:85]
X_test = X_scaled[85:]
# ← Val/test statistics influenced the scaler

# ✓ CORRECT: Fit scaler only on train
scaler = StandardScaler()
scaler.fit(X_train)  # Fit ONLY on train
X_train_scaled = scaler.transform(X_train)
X_val_scaled = scaler.transform(X_val)
X_test_scaled = scaler.transform(X_test)
# ← Train mean/std used for all; clean separation
```

#### 2. Feature Selection Leakage

```python
# ✗ WRONG: Select features on all data
important_features = select_top_k_features(X, y, k=10)  # Selects on all 100 examples
X_train = X[:70][important_features]
X_val = X[70:85][important_features]
# ← Feature selection influenced by val examples

# ✓ CORRECT: Select features on train only
important_features = select_top_k_features(X_train, y_train, k=10)  # Selects on train only
X_train = X_train[important_features]
X_val = X_val[important_features]
```

#### 3. Hyperparameter Tuning via Test Set

```python
# ✗ WRONG
models = []
for lambda in [0.1, 0.01, 0.001]:
    model = train(X_train, y_train, lambda)
    test_acc = evaluate(model, X_test, y_test)
    models.append((lambda, test_acc))
best_lambda = max(models, key=lambda x: x[1])
print(f"Best lambda: {best_lambda}, Test accuracy: {test_acc}")
# ← Tuned on test set!

# ✓ CORRECT
models = []
for lambda in [0.1, 0.01, 0.001]:
    model = train(X_train, y_train, lambda)
    val_acc = evaluate(model, X_val, y_val)
    models.append((lambda, val_acc))
best_lambda = max(models, key=lambda x: x[1])
# Retrain on train with best lambda
final_model = train(X_train, y_train, best_lambda)
test_acc = evaluate(final_model, X_test, y_test)
print(f"Best lambda: {best_lambda}, Test accuracy: {test_acc}")
# ← Tuned on val; evaluated on test
```

#### 4. Temporal Leakage (Time-Series)

```python
# ✗ WRONG: Shuffle data, random split
X_shuffled = shuffle(X)  # Loses temporal order
X_train = X_shuffled[:70]
X_test = X_shuffled[70:]
# ← Training on future data to predict past

# ✓ CORRECT: Temporal order
X_train = X[:70]  # Past
X_val = X[70:85]  # Recent past
X_test = X[85:]   # Future
# ← Train on past, test on future
```

## When to Use Train/Val/Test vs. Cross-Validation

### Train/Val/Test: Best for

- **Large datasets** (>10K examples) — single split is stable; CV overhead not needed
- **Expensive models** (neural nets, large ensembles) — CV requires $k$ times more training
- **Already have val/test sets** (e.g., Kaggle competition provides them)

### Cross-Validation: Best for

- **Small to medium data** (<10K examples) — single split is noisy; CV stabilizes estimate
- **Limited compute** — Can't afford $k$ times more training
- **Need confidence interval** — CV gives std dev across folds

**Hybrid:** Use CV on train set (nested CV) for small data, keep test set fixed for final evaluation.

---

## Practical Split Sizes

### For Large Data (>10K examples)

| Dataset Size | Train | Val | Test |
|---|---|---|---|
| 10K | 8K (80%) | 1K (10%) | 1K (10%) |
| 100K | 80K (80%) | 10K (10%) | 10K (10%) |
| 1M | 800K (80%) | 100K (10%) | 100K (10%) |

### For Small Data (<1K examples)

| Dataset Size | Recommendation |
|---|---|
| <50 | 3-fold CV, no test set (or LOO-CV) |
| 50-200 | 5-fold CV, optional small test set |
| 200-1K | 5-fold CV on full data, optional fixed test set |

## The Workflow

```
1. Split: (train 70%, val 15%, test 15%)

2. Explore train set
   - EDA
   - Feature engineering
   - Preprocessing

3. Try models & hyperparams on train/val
   Train on train
   Evaluate on val
   Tune hyperparams
   (Never look at test)

4. Select best model

5. Retrain on train+val
   (Optional: gives slightly more data)

6. Final evaluation on test
   Report once
   Done!
```

## Common Pitfalls

| Pitfall | Problem | Fix |
|---------|---------|-----|
| Scaling before split | Scaler learns from test; leakage | Split first, fit scaler on train only |
| Tuning hyperparams on test set | Test accuracy is biased; overfitting to test | Tune on val; evaluate on test |
| Reporting val accuracy as test accuracy | Misleading; val was used to tune | Always report test accuracy |
| Small val set (e.g., 1%) | Noisy; hyperparameter selection unreliable | Use val = 10-15% for stability |
| Too large val set (e.g., 50%) | Train set too small; underfitting | Use val = 10-15% |
| Shuffling time-series data | Temporal leakage | Preserve temporal order |

## Interview Questions

**Q: Why do you need three separate train, val, and test sets? Why not just train and test?**

Train/test only: If you tune hyperparameters by looking at test results, you optimize for that test set, making reported performance biased. Test set is no longer "held-out." With train/val/test: Train learns parameters; val tunes hyperparams; test gives honest evaluation. Test is truly unseen because hyperparameter decisions were made on val. See [[15.4_Cross_Validation_Strategy]] for alternative (CV) approach.

---

**Q: What is data leakage and give an example.**

Data leakage: Information from val or test sets influences training, making performance estimates biased. Example 1: Fit scaler on all data (including test) before splitting. Scaler learns mean/std from test examples → when test data is standardized, it's already been "seen" by the scaler. Example 2: Select features by running statistical tests on all data. Features selected are influenced by test examples. Fix: Always split first, then fit preprocessing on train only. See [[Common Mistakes in ML#1 - Data Leakage]].

---

**Q: If you have 1000 examples, how would you split into train/val/test?**

Typically 70/15/15: Train 700, Val 150, Test 150. Exact split depends on problem: More val if extensive hyperparameter tuning; more test if want low-variance final estimate. With only 1000 examples, consider 5-fold CV instead (more stable). Time-series: Temporal split (past 70%, recent 15%, future 15%). Imbalanced: Stratified split (preserve class distribution in each set). See [[15.4_Cross_Validation_Strategy]].

---

**Q: Is it okay to retrain the final model on train+val together before testing?**

Sometimes. After selecting best hyperparams via val set, retraining on train+val can give a slightly better model (more training data). But: (1) Costs more compute. (2) No val set to debug overfitting. (3) Early stopping harder without val set. (4) For small data, val examples matter. Best practice: Keep separate. Only retrain on train+val if data is large and hyperparams are fixed. See [[15.4_Cross_Validation_Strategy]].

---

**Q: If you shuffle a time-series dataset and then split into train/test, what happens?**

Temporal leakage. Shuffling destroys temporal order. If you train on random examples and test on random examples, training data includes future examples relative to test data. Model learns to use future information (unrealistic). In production, future data isn't available. Solution: Preserve temporal order. Train on past, test on future. Use forward-chaining CV for time-series. See [[15.4_Cross_Validation_Strategy]].

## One-line Summary

> Three-way split (train to learn, val to tune hyperparams, test to evaluate) prevents data leakage and biased estimates; always split first, fit preprocessing on train only, and never make decisions based on test set — use CV instead for small data.
