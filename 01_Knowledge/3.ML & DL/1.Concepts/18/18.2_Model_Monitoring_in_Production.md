# Model Monitoring in Production

## What is it?

**Monitoring** tracks model performance over time. Alert when performance degrades. Enable quick response (retraining, rollback, investigation).

**Key metrics:** Accuracy, precision, recall, latency, system health, data quality.

---

## Monitoring Strategy

### 1. Real-Time Dashboards

Track live predictions + performance.

```python
# Log each prediction
log_prediction(
    user_id=user_id,
    timestamp=time.time(),
    features={...},
    prediction=prediction,
    prediction_prob=prob,
    actual_label=None  # Added later when ground truth available
)

# Compute daily metrics
daily_accuracy = compute_accuracy(logs_today)
daily_precision = compute_precision(logs_today)

# Alert if drops
if daily_accuracy < 0.90:
    alert(f"Accuracy dropped to {daily_accuracy}")
```

### 2. Performance SLA (Service Level Agreement)

Define acceptable performance. Example:
- Accuracy ≥ 90%
- Latency ≤ 100ms
- Uptime ≥ 99.9%

Alert if breached.

### 3. Ground Truth Labeling

Collect ground truth to compute actual metrics. Challenges:
- **Delay:** Labels available days/weeks later (fraud detection)
- **Cost:** Manual labeling expensive
- **Bias:** Sample might not be representative

Solutions:
- Sample subset for labeling (80% confidence)
- Use proxy metrics (clicks, conversions)
- Active learning (label hard examples)

### 4. Alerting Strategy

Define thresholds; trigger alerts.

```python
if accuracy < 0.85:
    alert_level = "critical"  # Immediate action
elif accuracy < 0.90:
    alert_level = "warning"   # Monitor closely
else:
    alert_level = "ok"        # All good
```

---

## Metrics to Monitor

| Metric | Purpose | Alert Threshold |
|--------|---------|---|
| Accuracy | Overall correctness | < 85% |
| Precision | False alarms | < 80% |
| Recall | Missed positives | < 75% |
| Latency | Response time | > 500ms |
| Error rate | System failures | > 1% |
| Data quality | Missing/outlier % | > 5% |
| Prediction distribution | Drift detection | KS test p < 0.05 |

---

## Production Monitoring Stack

**Components:**
1. **Logging:** Record predictions, features, ground truth
2. **Storage:** Database (PostgreSQL, BigQuery) to persist logs
3. **Computation:** Batch jobs to compute daily/weekly metrics
4. **Visualization:** Dashboard (Grafana, Datadog) to view trends
5. **Alerting:** Notification system (Slack, PagerDuty) for breaches

**Open source:** Evidently, Whylabs, Arize

## Interview Questions

**Q: What metrics should you monitor for a production model?**

(1) **Performance:** Accuracy, precision, recall (compute via sampled ground truth). (2) **System:** Latency, error rate, uptime. (3) **Data quality:** Missing %, outliers, distribution shift (KS test). (4) **Predictions:** Prediction distribution (detect concept drift). Set SLAs per metric (accuracy ≥ 90%, latency ≤ 100ms). Alert if breached. Daily/weekly checks sufficient for most systems; real-time for sensitive applications (fraud). See [[18.1_Data_Drift_and_Concept_Drift]].

---

**Q: Ground truth labels arrive 2 weeks late. How do you monitor model performance daily?**

Use proxy metrics: (1) **Sample subset:** Label 10% of daily predictions; extrapolate. (2) **Proxy labels:** Clicks, conversions, returns (correlate with true accuracy). (3) **Model confidence:** Declining confidence may indicate drift. (4) **Input distribution:** Drift detection via KS test (indirect, but cheap). (5) **Combine:** Use multiple signals. Recompute full metrics weekly when labels arrive. See [[18.1_Data_Drift_and_Concept_Drift]].
